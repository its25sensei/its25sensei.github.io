Human–AI trust, verification, and interaction design

I study how people come to trust AI systems through what interfaces show them: citations, source statements, and confidence cues that look like evidence but may not be checkable. My work combines behavioral experiments with interaction design, with the goal of building interfaces that help people's trust match the evidence behind an AI's output.

Status of the work. No human-participant data have been collected yet. All results shown below come from simulated data and demonstrate that the analysis pipelines work; they are not empirical findings.

Interpretive

Social-scientific research on how people interpret AI-generated evidence, and the study interface built to test it. This is the primary focus of my work.

Writing sample · Source-Based AI Recommendation Explanations

Research proposal9 pagesIndependent

A proposal for a five-condition between-subjects experiment. An AI shopping assistant explains the same recommendation using a user's past behavior, other customers' reviews, product features, a mix of sources, or no stated source. The study tests whether an explanation that feels more relevant because it reveals personal data also raises privacy concern, and how these responses shape trust and reliance.

The proposal covers theory, hypotheses, stimuli, measures, power analysis (minimum N = 305; recruitment target N = 360), and a two-stage pilot protocol.

Verification Theater · Study design

Experiment designIndependent

Every participant chooses between two laptops and receives the same incorrect AI recommendation. Only the support attached to it varies:

  • Reasoning only, with no sources;
  • Professional-looking sources that cannot be verified;
  • Genuine, verifiable sources whose interpretation is misleading.

The design logs which sources participants open, so verification is observed as behavior rather than inferred from self-report. The third condition asks the question I care about most: is being checkable enough, or can real sources still lend credibility to wrong advice?

Design decisions

The recommendation card is a single shared component, so its wording, size, and position are identical in every condition. The source link has the same appearance and hover state in C2 and C3; only what happens on click differs, so the conditions cannot be told apart without checking. Scale labels and feedback text are neutral: the page echoes the selected number and never evaluates it.

Design exploration: a second AI model

The prototype also contains three screens that are not part of the current study. They sketch an interface for a follow-up question: do people treat agreement between AI models as independent confirmation? A second model either agrees with the incorrect recommendation, disagrees with it, or agrees while the interface notes that the two models are not independent. Each screen offers a link to re-open the specifications, so that checking can be observed as behavior.

The question builds on findings that people follow unanimous AI panels more readily (Tsuchiya & Baba, 2026), that a disagreeing second opinion reduces overreliance but also reliance on correct advice (Lu, Wang & Yin, 2024), and that language models often make the same mistakes (Kim et al., 2025). This is an interface concept only; hypotheses, measures, and a power analysis have not been developed.

Confidence-calibration simulation

Python · JupyterSimulated dataIndependent

A design probe on the system side of the same problem: how far an AI's stated confidence can drift from its accuracy. It compares an overconfident and a confidence-matched condition using expected calibration error (ECE: 0.275 vs. 0.026 in one simulated run). It led to the question that connects my projects: does a well-calibrated system actually help users calibrate their trust?

Benford's Law screening of SEC filings

Python · pandas · scipy~3.2M valuesIndependent

I applied Benford's Law screening to approximately 3.2 million values from SEC XBRL filings and cross-validated flagged observations against an independent accrual-based indicator. The anomalies that survived reflected the reporting structure of business development companies rather than manipulation: a statistically real signal that, read without its context, would have suggested misconduct that was not there.

SourceLens · Explainable product recommendations

Team projectStreamlit · Python · FigmaIn progress

A headphone recommendation system in which every recommendation reason links to the specific evidence behind it: a product specification, an attributed review excerpt, or the user's own stated preference. Users can inspect each reason–source connection directly instead of relying on a general explanation.

My contribution: project manager and UI/UX designer. I led requirements and project coordination and designed the interface in Figma. The recommendation engine and evidence mapping were built by Chaitanya Mehta; the front end, integration, and testing by Shuonan Chen.
